# 多猎头重复投递记录设计

## 目标

允许同一求职者向同一岗位的多家已授权猎头投递，同时保证该岗位只产生一条候选人主投递。首条有效投递进入岗位候选人库；后续猎头保留一条仅自己可见的重复投递记录，并只得到“该人选已入库”的结果。

本批次只处理投递归属、重复记录、权限隔离和并发一致性，不调整推荐反馈终态、企业结算或入职流程。

## 业务规则

### 主投递

- 主投递是同一 `job_id + candidate_id` 的第一条有效投递。
- 主投递绑定提交时选择的 `assignment_id`、发布该岗位的猎头 `publisher_user_id`、猎头工作候选人和固定工作简历。
- 主投递可进入筛选、推荐和企业反馈流程。
- 主投递的详细候选人资料、简历、审核备注和推荐状态仅对所属猎头及其有权限的机构成员可见，企业只在推荐交付后查看固定快照。

### 重复投递

- 重复投递是同一 `job_id + candidate_id` 在已有主投递后，由另一家有效承接猎头提交的记录。
- 重复投递绑定当前提交的 `assignment_id` 和当前猎头，用于留痕、统计和向求职者展示投递结果。
- 重复投递不创建 `working_candidate`、`working_resume`，不进入筛选、推荐或企业反馈流程。
- 重复投递所属猎头只能查看自己的记录、提交时间、所选岗位和脱敏提示“该人选已入库”；不得看到主投递猎头、企业私有字段、主投递状态、简历正文或推荐反馈。
- 求职者可以看到自己的重复投递记录，但不看到其他猎头或企业的私有信息。

### 同一猎头再次投递

- 同一 `job_id + candidate_id + publisher_user_id` 已存在任何投递记录时，新的投递直接返回冲突错误，不新增记录。
- 前端将该错误显示为“你已提交过该岗位的人选记录”，避免用户误解为平台故障。

## 数据模型

在 `applications` 增加：

- `record_kind`：`primary` 或 `duplicate`，默认 `primary` 以兼容已有数据。
- `canonical_application_id`：主投递 ID；主投递指向自身，重复投递指向主投递。
- 可选的 `duplicate_message` 不落库，接口按权限生成固定提示，避免存入可能泄露信息的文本。

约束调整为：

- 唯一约束由 `job_id + candidate_id` 调整为 `job_id + candidate_id + publisher_user_id`。
- `record_kind=primary` 在同一 `job_id + candidate_id` 下最多一条，由事务锁和数据库约束共同保证。
- 旧数据迁移时，所有已有记录设为 `primary`，`canonical_application_id` 回填为自身；如发现历史重复数据，迁移先失败并输出冲突清单，不自动合并。

## 创建流程

1. 校验岗位、承接关系、岗位版本、求职者本人和简历归属。
2. 锁定岗位与候选人范围内的投递记录。
3. 查找同一 `job_id + candidate_id` 的主投递。
4. 若无主投递，创建主投递、猎头工作候选人和固定工作简历。
5. 若已有主投递且当前猎头不是主投递所属猎头，创建重复投递，不复制候选人和简历。
6. 若当前猎头已有投递，返回 409。
7. 提交后返回统一响应字段；主投递返回正常投递状态，重复投递返回 `record_kind=duplicate` 和 `visibility_message=该人选已入库`。

并发场景下，两个猎头同时首次投递时只能有一个事务创建主投递，另一个事务必须在唯一约束或锁冲突后重新读取主投递并创建重复投递。

## 查询与权限

- 求职者 `/applications/me` 返回自己的主投递和重复投递，重复投递不返回 `publisher_user_id`、`working_candidate_id` 或任何主投递标识。
- 猎头 `/applications` 只返回自己发布岗位收到的主投递，以及自己创建的重复投递；重复投递使用专用脱敏输出模型。
- 猎头候选人管理、推荐创建、简历下载和投递状态推进只接受 `primary` 记录。
- 企业端不读取重复投递记录。
- 管理员可查看全部记录用于审计，但接口明确标出记录类型和主投递关联。

## 前端交互

- 岗位投递说明改为“同一岗位可选择不同猎头投递；若该人选已被其他猎头收录，系统会保留本次重复投递记录，但不会重复进入候选人筛选”。
- 投递成功页和“我的投递”对重复记录显示“该人选已入库”，不显示首投方。
- 猎头候选人投递列表将重复记录显示为“重复投递”，隐藏下载简历、候选人档案、转为推荐和推进状态操作。
- 409 同猎头重复提交显示为业务提示，不显示数据库约束或内部 ID。

## 验收标准

1. 空数据下第一家猎头投递创建一条 `primary`，并创建工作候选人和工作简历。
2. 第二家猎头投递创建一条 `duplicate`，不新增工作候选人和工作简历。
3. 第二家猎头读取自己的记录时只看到“该人选已入库”，看不到首投方和主投递状态。
4. 同一猎头第二次投递返回 409，数据库不增加记录。
5. 两个猎头并发首次投递后，数据库恰好一条 `primary`，其余为 `duplicate`。
6. 主投递仍可正常审核、创建推荐和进入企业反馈；重复投递无法调用这些操作。
7. 旧数据迁移检查通过；发现历史重复时停止迁移并输出冲突清单。
8. 后端针对性测试、前端构建、真实 API 和至少两个猎头角色的浏览器验证均通过。

## 风险与边界

- 本批次不自动把重复投递转为主投递。主投递猎头拒绝或撤回后的重新归属规则另行设计，避免在本批次引入候选人所有权争议。
- 不向后续猎头暴露“首投猎头是谁”或“主投递当前进行到哪一步”，避免形成跨猎头侧信道。
- 不改正式数据库；先在隔离数据库完成迁移演练和回归。
